# 사람이 진행할 설정: 어려운 순서와 실행 방법

2026-11-02. 난이도는 계정 권한·서버 변경·여러 담당자 조율을 합친 기준이다. 아래 순서는 난이도순이며, 앱을 빨리 완성하려면 쉬운 지도 키 발급·백엔드 데이터 요청도 병행하면 좋다. 서버에 이미 설정된 값이 있는지는 담당자가 먼저 확인한다.

공통 Android 패키지: `com.workernotfound.app`. 프론트 코드는 에이전트가 구현한다. 서버 비밀키는 서버 담당자가 보관하고 프론트에 전달하지 않는다.

| 순서 | 항목 | 난이도 | 실제 작업자 |
|---|---|---|---|
| 1 | 단말 푸시 전체 연결 | 매우 어려움 | Firebase/푸시 프로젝트 소유자 + 백엔드 + 프론트 |
| 2 | Toss 테스트 결제 | 매우 어려움 | Toss 프로젝트 소유자 + 백엔드 + 프론트 |
| 3 | 카카오·네이버 로그인 | 어려움 | 각 개발자 앱 소유자 + 백엔드 + 프론트 |
| 4 | Play 배포/서명 (스토어 배포할 때만) | 어려움 | 배포 계정 소유자 + 프론트 |
| 5 | 이메일·SMS·사업자 인증 | 어려움 | 백엔드/발신 서비스 계정 소유자 |
| 6 | 계약서·신뢰도 등 미제공 계약 | 중간 | 기획/백엔드 |
| 7 | Naver 지도 키 | 비교적 쉬움 | Naver Cloud 계정 소유자 |
| 8 | 실물 휴대폰 테스트 | 비교적 쉬움 | 테스트 담당자 + 프론트 |
| 9 | 업종·점주·근무 데이터 요청 | 요청 자체는 쉬움 | 사용자 → 백엔드 담당자 |

## 1. 푸시: FCM을 사용하기로 팀에서 결정한다면

1. [Firebase 콘솔](https://console.firebase.google.com/)에 프로젝트 소유 계정으로 로그인한다. 기존 백엔드 팀 프로젝트가 있는지 먼저 확인한다.
2. 프로젝트를 선택하거나 생성하고 Android 앱을 추가한다. 패키지에 `com.workernotfound.app`을 입력한다.
3. 앱 설정 파일 `google-services.json`을 내려받아 프론트 담당자에게 전달한다. 서버용 서비스 계정 개인키와 다른 파일이다.
4. 백엔드 담당자에게 같은 프로젝트에서 FCM 발송 권한/서버 인증을 설정하고, 기기 토큰 등록·갱신·로그아웃 해제 계약을 제공해 달라고 요청한다. 현재 BE에는 알림 목록 저장/조회만 확인되며 단말 전송은 미연결이다.
5. 프론트는 FCM 수신, Android 알림 권한, 알림 채널, 클릭 후 해당 업무 이동과 토큰 갱신을 구현한다.
6. 실제 휴대폰에서 앱 실행 중/백그라운드/프로세스가 종료된 상태를 각각 테스트한다. 사용자가 강제 중지한 상태와 일반 종료는 구분한다.

완료 기준: 서버에서 특정 테스트 계정의 기기에 보낸 알림이 도착하고, 클릭하면 권한 있는 해당 화면으로 이동한다. 콘솔 테스트 메시지만 도착한 상태는 업무 이벤트 연결 완료가 아니다.

[공식 Android 등록](https://firebase.google.com/docs/android/setup) · [FCM 시작하기](https://firebase.google.com/docs/cloud-messaging/android/get-started?hl=ko)

## 2. Toss 테스트 결제

1. 백엔드 담당자에게 “현재 사용하는 Toss 테스트 프로젝트/키가 있나요? TOSS_ENABLED와 서버 테스트 secret 설정이 되어 있나요?”라고 묻는다.
2. [Toss 개발자센터](https://developers.tosspayments.com/)에서 그 프로젝트를 선택한다. 프론트에는 해당 프로젝트의 **테스트 공개 client key**만 제공한다. 다른 샘플 프로젝트의 키를 섞지 않는다.
3. 프론트·백엔드가 성공/실패 URL과 앱 복귀 방식을 합의한다. URL을 임의로 정해 등록하지 말고 실제 처리할 서버/앱 경로와 일치시킨다.
4. 백엔드 담당자가 공개 웹훅 `https://api.15-165-106-227.sslip.io/api/payments/webhooks/toss`의 배포/수신 설정을 확인한다.
5. 프론트가 결제창→성공 정보 전달→서버 confirm→주문 상태 재조회→공고 OPEN 확인을 구현한다. 결제창 성공만으로 공고 게시 성공을 표시하지 않는다.
6. 테스트 OWNER·사업장·카테고리와 공고를 준비해 테스트 환경에서 성공/취소/실패/앱 복귀를 확인한다. 실결제 키로 전환하지 않는다.

완료 기준: 동일 공고/주문/금액을 서버가 확인하고 공고 공개 상태까지 반영된다.

[공식 결제창 연동](https://docs.tosspayments.com/guides/v2/payment-window/integration)

## 3. 카카오·네이버 로그인

1. [카카오 개발자센터](https://developers.kakao.com/)와 [네이버 개발자센터](https://developers.naver.com/)에서 기존 팀 앱을 찾거나 소유자가 앱을 등록한다.
2. 백엔드에 현재 등록된 OAuth client ID가 어느 앱의 것인지 확인한다. 지도 Client ID는 네이버 로그인 키로 사용할 수 없다.
3. 프론트·백엔드가 인증 흐름을 먼저 맞춘다. 현재 BE는 `authorizationCode`, `redirectUri`, `state`, `deviceId`를 받는다. 네이티브 SDK가 반환하는 access token을 이 요청의 code에 넣으면 안 된다.
4. 확정한 흐름에 맞춰 로그인 활성화, callback/redirect URI, Android 플랫폼 정보를 등록한다. Android SDK 방식에 필요한 키해시/서명 지문은 프론트 담당자가 추출한다.
5. 개발/검수 상태에서 허용된 테스트 계정을 등록해야 하는지 확인한다. 제공자에서 요구하는 동의 항목도 실제 가입에 필요한 정보와 맞춘다.
6. 프론트가 앱 복귀와 성공/취소/오류 처리를 구현한 후 신규 가입자/기존 가입자를 각각 검증한다. 소셜 가입도 BE의 휴대폰 인증 조건이 남는다.

완료 기준: 앱에서 시작한 인증이 앱으로 복귀하고 BE가 OWNER/WORKER 세션을 발급한다. 보류 중인 Google 계정은 이 설정에 사용하지 않는다.

[카카오 설정](https://developers.kakao.com/docs/ko/kakaologin/prerequisite) · [네이버 가이드](https://developers.naver.com/docs/login/devguide)

## 4. 스토어 배포를 할 경우에만

1. 발표용 APK 직접 전달인지 Play 배포인지 정한다. APK 직접 테스트에는 Play 계정이 필요 없다.
2. Play 배포라면 조직/개인 개발자 계정 소유자가 등록 절차를 진행하고 프론트 담당자를 초대한다.
3. 앱 패키지를 유지할지 확정한 뒤 release 서명/업로드 키와 소유·백업 방법을 정한다. 키 파일/암호를 Git에 넣지 않는다.
4. 앱명·설명·아이콘·스크린샷·문의처와 Play Console에서 요구하는 정책/데이터 관련 정보를 실제 기능에 맞춰 준비한다.
5. 프론트가 서명된 산출물과 해당 서명에 맞는 외부 서비스 등록을 확인하고 내부 테스트부터 배포한다.

현재 release signing 미설정. 서명키 생성/빌드 자체는 프론트 담당자가 할 수 있으며 소유 계정과 배포 방식 결정이 사람의 입력이다.

## 5. 가입·복구 인증 서비스

1. 백엔드에 기존 설정부터 확인해 달라고 요청한다: SMTP, SOLAPI 발신, 국세청 사업자 조회.
2. 메일은 서버에서 발송할 계정과 서비스가 요구하는 인증 설정을 준비하고, SMS는 계정과 인증된 발신번호를 준비한다.
3. 국세청 API 사용 권한/서비스 키는 서버 담당자가 설정한다. 실제 점주 가입에는 사용 허가된 정상 영업 사업자 정보도 필요하다.
4. 서버 담당자가 `AUTH_MAIL_*`, `AUTH_SOLAPI_*`, `AUTH_VERIFICATION_SMS_FROM`, `NTS_BUSINESS_API_SERVICE_KEY`를 서버 환경에 설정한다. 이 값은 프론트에 보내지 않는다.
5. 동의한 테스트 수신자의 메일/전화로 발송·코드 검증·가입/복구 성공을 확인한다. 현재 사용자에게 가입용 정보가 없으므로 점주 seed 생성은 별도 요청한다.

완료 기준: 실제 수신과 코드 검증 성공. 발송 버튼 API가 있다는 것만으로 외부 설정 완료로 표시하지 않는다.

## 6. 계약서·신뢰도 등

1. 기획/백엔드에 전자 근로 계약서의 실제 내용과 문서 조회/서명 범위를 요청한다.
2. 신뢰점수·위험등급·개인화 추천의 공개 응답과 정책을 확인한다. 프론트가 점수/등급을 임의 계산하지 않는다.
3. 실시간 위치 공유가 필요하면 참여자별 전송/조회 계약, 공유 시작/종료·주기를 백엔드와 정한다. 지도 SDK 연결과 별도 업무다.
4. 프론트는 확인된 계약만 구현한다. 리뷰는 이미 공개 API가 있으므로 화면/기한을 서버 계약에 맞춰 별도로 구현할 수 있다.

## 7. 네이버 지도 Client ID 발급

1. [Naver Cloud 콘솔](https://console.ncloud.com/)에 로그인한다.
2. Services에서 **Application Services → Maps**를 찾아 이용 신청/애플리케이션 등록으로 들어간다.
3. **Dynamic Map**을 선택한다. Android 앱 패키지 이름에 **`com.workernotfound.app`**을 등록한다.
4. 등록한 애플리케이션의 인증 정보에서 **Client ID/키 ID**를 확인해 프론트 담당자에게 전달한다. 네이버 로그인 앱 키와 구분한다.
5. 프론트가 gitignore된 로컬 설정으로 주입하고 SDK·핀·위치·오류 처리를 구현한다. 주소 변환 등 다른 API 사용은 별도 서비스 활성화가 필요할 수 있다.

완료 기준: 앱 화면에 실제 지도 타일이 나오고 실제 좌표에 핀이 표시된다. Client ID 발급만으로 현재 도식 화면이 자동으로 바뀌지는 않는다.

[공식 발급 절차](https://navermaps.github.io/android-map-sdk/guide-ko/1.html)

## 8. 실제 Android 단말

1. 테스트에 사용할 폰과 USB 케이블을 준비하고, 개발자 옵션/USB 디버깅을 켠다. 연결 시 해당 컴퓨터를 허용한다.
2. 프론트 담당자가 연결을 확인하고 테스트 APK를 설치한다. 이 과정은 에이전트가 진행할 수 있다.
3. 위치 정확도/거부/GPS 끔, 카메라 취소, 백그라운드 푸시, 두 계정 채팅을 확인한다.
4. 실제 출근은 합의된 테스트 근무 시간/위치/반경으로만 검증한다. 계정이 없으면 데모 확인과 실서버 검증을 구분한다.

## 9. 백엔드에 복사해서 보낼 요청

후속 확인: 테스트 OWNER 2개/WORKER 2개를 전달받아 로그인과 점주 사업장 연결까지 검증했다. 아래 요청에서 계정을 새로 만들 필요는 없으며 업무 데이터와 업종·결제 설정이 우선이다.

> 전달해 주신 계정 4개는 로그인과 점주 사업장 연결을 확인했습니다. 실제 category ID/name 목록의 공식 계약 또는 조회 API, 이 계정들에 연결된 테스트 공고/근무/매칭/채팅방을 부탁드립니다. 근무 시간·좌표도 알려 주세요. Toss는 서버 테스트 설정 여부와 대응하는 공개 client key·복귀/웹훅 설정을 확인 부탁드립니다. 메일/SMS/국세청은 서버 설정 및 실제 동작 여부만 확인해 주시고 서버 비밀키는 전달하지 않으셔도 됩니다. 푸시는 제공자와 기기 토큰 등록/발송 계약이 필요합니다.

프론트 도메인이나 localhost 주소는 native Android REST 연결에 필요 없다. OAuth/결제 복귀 주소가 필요해지는 경우에는 해당 기능 담당자끼리 경로를 정한다.
